## 原生绑定边界追加

`tools/trace_native_scene_type.py` 以锁定 SHA 的 `libclient.so` 检查 ELF 段和 CPython 2 32 位类型结构候选，输出 `native-scene-type.json`。REA 原生分析 provider 的既有不可用限制仍存在；本轮采用本地字节读取/LLVM 辅助分析，不标作 REA 运行证据。

- 文件偏移 `0x2984978`、VA `0x2985978` 的类型结构候选以 `world.scene` 名称、实例大小 `0x30` 和初始化 Thumb 指针 `0x9e27a1` 交叉定位。
- 对应 `tp_methods` 槽指向 `0x30ee228`，位于 ELF PT_LOAD 的文件内容之外、零填充内存区。因此不能直接在文件里将它读成已经填好的 Python 方法表；需要追踪初始化写入或在获准的原生运行环境观察。
- 文件 `0x2ac21c4` 的内嵌 load 文档说明 source 支持字符串/shared_object，返回 success 与 layer_id。它没有说明后缀替换或路径别名，不能据此判定 `city_battle_3` 的加载行为。

上述类型结构检查当时尚未关联具体 `load` 包装器；后续关联结果见下节。

## load 注册与原生文件边界

运行 `python tools/trace_native_scene_load.py`，输出 `native-scene-load.json` 和七段带 SHA-256 的 LLVM 反汇编。工具固定校验原生库 SHA、注册字面量、初始化数组成员、资源单例 GOT 重定位及加载器字符串；它不执行目标代码。2026-10-14 运行通过。

1. `.init_array` 包含 `0x71d971`；其初始化代码将名称 `load`、函数 Thumb 指针 `0x9e8c3d` 和文档指针写入方法记录 `0x30ee228`。因此已从名称交叉引用推进到确切注册入口，不再仅凭邻近字符串猜测。
2. 包装器 `0x9e8c3c` 在 `self+0x10` 有效时转入 `0x9e2c30`。字符串分支调用 `0x11df27c`，将其结果传至场景虚表 `+0x24` 或 `+0x2c`；非字符串 shared-object 分支用 `+0x28`。
3. `neox::world::Scene` RTTI 候选虚表位于 `0x2975e9c`。其 `+0x24` 实现 `0x7e56d4` 将输入路径交给资源单例虚表 `+0x40`（调用点 `0x7e5702`），成功后把返回句柄交给场景虚表 `+0x28`。该资源单例由 GOT `0x2a88bdc` 引用零填充区 `0x3034954`。
4. 同一候选虚表 `+0x2c` 实现 `0x7f2228` 将原输入路径传给 `0x8379d0`。后者保存路径到 r5，在 `0x837a18` 原样作为 r1 交给另一单例虚表 `+0x38`，后续解析返回数据并查询 `SceneHeader`；失败分支包含 `Unable to open file %s`。此文件接口单例由 GOT `0x2a88c60` 引用 `0x303495c`。两项 GOT 均有独立 `R_ARM_RELATIVE` 重定位验证。

这仅证明上述候选实现到下一层接口的参数传递，没有证明底层文件系统/资源单例不做映射，也没有证明所有运行时对象都使用此候选虚表。不能仅因分配了加载对象便将第二条路径命名为异步加载。LLVM 输出的远距离最近符号标签不能当作这些函数的真实名字。

下一步需定位两个零填充单例的初始化与实际虚表，追踪 `+0x40`/`+0x38` 的实现；无需重复扫描已经确认的 Python 注册代码。教程 `city_battle_3` 仍为精确路径未匹配，不能升级为资源绝对缺失结论。本次没有新增游戏画面或原客户端运行验证。

## 文件服务身份与路径处理追加

`python tools/trace_native_scene_filesystem.py` 已运行通过，输出 `native-scene-filesystem.json` 与六段有 SHA-256 的反汇编。校验源库 SHA、ADR 指令、服务名称、写入地址、RTTI 类型与虚表槽；不执行原程序。

- 注册代码 `0x7c9404` 起通过服务注册表的 `+0x10` 获取 `IAsyncLoader_1.2` 并存到 `0x3034954`，获取 `IResFileSystem_1.3` 并存到 `0x303495c`。前一节两个未知单例现在有了明确接口名称。
- `ResFileSystem` RTTI 候选虚表为 `0x2973384`，其 `+0x38` 指向 `0x7ae76c`。这个短函数仅将 self 换成 `self+0x108` 的指针，保留 r1/r2/r3，尾调用新对象虚表 `+0`。
- `0x7adb7e` 起的依赖获取代码请求 `IFileSystem_1.8`，在 `0x7adb8a` 保存到 `self+0x108`。`FileSystem` RTTI 候选虚表 `0x2973664` 的 `+0` 指向 `0x7b2468`。
- 文件读取候选实现先复制输入路径，在 `0x7b24e8` 调用 `0x10c86bc`。输出状态有效时，将输出结构的 `+4` 字段交给下层 `0x10c679c`（调用点 `0x7b2510`）。因此不应笼统声称整个文件系统“原样使用路径”。
- `0x10c86bc` 调用 `0x10c89f0` 获得路径分段，在 `0x10c8800` 写出 `0x5c` 字节作为段间连接符。完整语法/特殊路径分支尚未还原。已有 `neox_resource_paths.resource_hash` 会将 `/` 转为 `\`，故该发现并不会单独改变教程路径精确查询无匹配的结果；未修改索引查询算法。

这些服务名称与 RTTI 关联仍是静态候选链，尚无原运行时服务注册表证明最终实例类型。下一步重点是路径拆分 `0x10c89f0` 的完整分支和 `0x10c679c` 下层归档查找，另一路 `IAsyncLoader_1.2` 的 `+0x40` 实现仍待追踪。没有证明 `city_battle_3` 绝对缺失，也没有新增原版场景画面。

## NPK 后端查表闭合

`python tools/trace_native_npk_lookup.py` 已通过。工具保存 `native-npk-lookup.json`、六段反汇编，校验 APK/ELF SHA、六个 PLT 符号的重定位、三种哈希函数 GOT 绑定、包头选择标记以及 17 个实际包头。

- `NXNpk` RTTI 候选虚表 `0x29c8758` 的 `+8` 指向 `0x10cc848`。这里直接将剩余路径的字符指针交给 PLT `0x69ee30`，其重定位符号明确为 `NpkReader::GetIndex(char const*)`，地址 `0x138d730`。本段没有后缀替换。
- `GetIndex` 用 `self+0x28` 的回调计算名称哈希，对 28 字节记录做 lower-bound 查找，并只在记录首字段等于哈希时返回。此函数内没有名称别名查找。
- `DoOpen` 在 `0x138d540` 写入该回调。它调用 `GetStringIDTypeByHeader`，通过已验证的 `memcmp` 对包头偏移 8 开始的 12 字节与 `00 00 00 00 00 00 00 00 01 00 00 00` 比较：相等返回类型 0，否则类型 2。
- `GetStringIDFunc` 的重定位证明类型 0 对应 `StringIDLegacy`（Thumb `0x18eaf6f`），类型 1 对应 `StringIDVS2012`，类型 2 对应 `StringIDMurmur3`。APK 内全部 17 个 NPK 均选择类型 0，与现有 Python 查询算法一致。
- `Open(Input*)` 经过 `0x16c5598` 的 Thumb/ARM 转接跳板进入 `DoOpen` 的 PLT；跳板中的 ARM 字节不能按 Thumb 乱码当成额外处理逻辑。

因此，在已静态定位的 NPK 后端分支中，教程三种挂载拆分均无匹配，不是查询选错包头哈希算法或 `GetIndex` 自带后缀改写导致。仍未观察原运行时挂载绑定，也不能排除上层其他分支、独立文件或 APK 外补丁资源。教程原场景继续列为当前输入的资源缺口，不可声称已恢复。
