# 黑潮之上完整重建开发计划

本文件是项目唯一的长期开发计划，后续直接更新任务状态、范围和验收结果，不再为每次开发新增记录文档。计划基线：2026-10-15。持续目标以本文件与根目录 README 中最新用户确认范围为准。

## 1. 最终交付与开发原则

交付能实际游玩的《黑潮之上》重建版：原版大厅、角色、卡牌战斗、世界线、养成及相关系统；可维护的服务端和独立游戏管理后台；可重新打包并新增玩法的工程。客户端从开始就按 Windows、macOS、Android、iOS 四平台设计。

| 端 | 确定方案 | 交付要求 |
| --- | --- | --- |
| 游戏客户端 | Unreal Engine 5.8.3；工程 `clients/unreal5 5.8/Hczs.uproject` | 原 APK 资源与行为对照、完整操作闭环、平台构建与实机验证 |
| 游戏服务端 | Node.js + MongoDB/Mongoose | 参考 `D:\project\so-im` 的统一连接、模型、服务分层；持久化、幂等、恢复、配置版本管理 |
| Admin 管理端 | 独立 Web 后台，参考 so-im 后台的组织方式 | 玩家管理、内容配置、运营操作、发布回滚、权限与审计；不能以恢复进度页代替管理系统 |
| 资源转换工具 | `tools/` 中可复用脚本与 UE 导入工具 | 同类资源批量恢复、依赖跟踪、可重复运行、失败可定位；不逐个手工重做全部角色 |

执行约束：

- 每个游戏功能先定位原 APK 的资源、配置、脚本入口与交互，再实现并对照画面。用户提供的原版视频截图也是视觉参考，但不等于完整运行证据。
- 原始资源优先直接转换。缺失内容明确列出，不能自创面板、任意特效或猜测规则后称为原版恢复。
- Cocos 已退出客户端主线，历史材料在 `legacy/cocos-poc`；不再扩建 Cocos 客户端。
- 先把艾尔莎做成合格样板，再通过公共管线覆盖全部角色。大厅使用真实 `home_stand_idle_1` 等大厅动作，不用战斗待机替代。
- 初期服务面向个人本地游玩，默认监听回环地址。原 APK、提取大资源、运行存档、密钥不提交版本库。so-im 只读参考。
- 测试通过、文件存在和能打开预览，分别不代表画面还原、玩法完成和四平台可交付。

## 3. 资源、模型与画面的完整工作包

### A. 公共提取与转换管线

建立统一依赖链：角色/场景/技能配置 → entity、LOD、模型与动画库 → 网格、骨骼、纹理、材质、特效、声音 → UE 资产 → 关卡/玩法引用 → 实际画面验收。

| 任务 | 实现内容 | 验收条件 |
| --- | --- | --- |
| A1 资产索引 | 统一原路径、NPK 位置、源哈希、类型、引用与输出路径 | 任意 UE 恢复资产能追溯原来源；共享依赖不重复提取 |
| A2 批处理 | 按资源类型执行转换、缓存、增量重建、错误重试、缺失报告 | 输入未变化时不重复转换；单个失败不阻断整批，错误定位到具体条目 |
| A3 导入规则 | 单位、轴向、正反面、骨骼绑定、材质槽、命名、LOD 和动画一致 | 重跑不会生成重复资产或覆盖人工修订；先备份再变更 UE 资产 |
| A4 缺口管理 | 区分未定位、索引存在但未提取、转换失败、包内缺失、依赖在线资源 | 每个缺口都有资源路径/配置字段和下一步，不能笼统写“已提取待接入” |
| A5 发布资源 | 原始资产与 AI 变体、平台压缩版本分别管理 | 可切回原图；构建仅携带实际依赖；许可证/来源信息保留在本地清单 |

每位角色必须通过以下各项，才能计入完整恢复数量：

1. 正确角色/服装/用途/LOD 绑定，几何、UV、材质槽、骨骼和蒙皮权重完整；没有歪站、穿帮、镜像、错脸、丢头发或丢武器。
2. 绑定姿态、动画坐标变换与角色朝向一致；脚底贴地、比例合理，不能靠倾斜整个 Actor 掩盖骨架问题。原视频参考本方在左、敌方在右，并结合具体关卡摄像机确认。
3. 正确的大厅站立、展示、触摸互动及相应语音；大厅动作与战斗动作分开关联。
4. 战斗待机、起手、攻击、技能、受击、死亡、胜利及实际配置的其他动作可播放，过渡不抽搐。根运动、武器挂点、脸部/头发/裙摆等按原资源能力恢复。
5. 卡牌、技能规则、目标类型、BUFF、终结技演出、特效与音效正确关联；角色能进入编队并完成战斗。
6. 默认与非默认服装各自验证；骨架共用不代表材质、动作或特效一定共用。未具备的服装不显示为可用成品。
7. 大厅、战斗、近景至少各一项画面对照；保存选择后重启能恢复；批量自动检查后仍须实际观察异常角色。

怪物/NPC 采用相同基础标准，按用途裁剪大厅/养成项。BOSS 另验多阶段、召唤、形态变化、受击部位和死亡演出，不用统一红闪或通用爆炸代替。

### D. 材质、光影、清晰度

先恢复原来的颜色、透明和卡通风格，再评估增强。不能用 UE 默认 PBR、强泛光或高曝光覆盖源材质错误。

| 项目 | 工作内容 | 验收重点 |
| --- | --- | --- |
| 原 Shader 映射 | 按材质族处理不透明、裁切、半透明、加法、双面、描边、溶解、UV 流动、扭曲 | 每类先做样本，确认后批量套用；原参数语义明确 |
| 纹理通道 | 正确区分颜色、法线、混合遮罩、粗糙度/其他数值通道、Alpha | sRGB、采样、通道与混合方式正确；法线/数值图不按普通图片 AI 补画 |
| 场景光照 | 追查原环境色、光照贴图、阴影、角色受光和场景效果 | 角色与场景一致，有合理接触阴影；消除未构建光照提示，不靠隐藏提示交付 |
| 卡通表现 | 按源材料处理明暗分区、轮廓、边缘光、头发/衣服高光 | 保持源美术风格；不因更换引擎变成另一种画风 |

| AI 高清化 | 只对需要的颜色纹理和位图图标生成独立高清变体 | 同视觉族轮廓、浅色边线、语义颜色、视觉大小一致；保留原图和切换途径 |

**当前必须优先修复的画面问题：**

- 城市场景云层显示成白色矩形。源 `plane_yun.gim` 的 `lancer2.fx` 材质使用 `TransparentMode=5` 和独立 `ALPHA_MASK`；当前转换没有完整保留其语义。先恢复遮罩、透明及流动，再验证排序和曝光。
- 幻眼魔方出现整块亮黄色。原提取颜色贴图是紫白色，需读回 UE 材质槽、参数与曝光定位原因，不把黄色当成源效果。

- 指向线/目标框、调试文字与卡牌遮挡明显偏离原画面。恢复原箭头贴图与弧形结构，移除正常游戏中的重建规则、卡牌 ID 等调试内容，校正手牌可读性。

### 4.1 世界线与序章的已知约束

- 原 `ActivityGroup == 0` 的 19 项包含序章和后续章节目录，不代表已解锁 19 章。
- 原进度字段 `activityDatas["2"]["3997"]["successTime"]` 在已检查逻辑中是成功次数条件，不能按时间戳处理；部分入口还判断键是否存在，不能预填全 0 后误解锁。
- 已定位入口链：Activity 2 → challenge 3997 → maze 3997 → battle 5000。Guide 1001 直接教学是另一条入口。
- `chess_xuzhang` 场景 239 是章节地图，不是战斗场景。地图 50002 的起点、挑战、终点节点需要按原坐标和事件接入。
- battle 5000 的基础场景 2081（`city_battle_3`）与 maze 3997 的加载覆盖 2133（`pszdu_battle_1`）存在运行优先级待核对；当前 `city_battle_1` 仅为本地展示适配。确认实际加载链后再验收首战场景一致。

### 4.2 出牌同步与即时反馈

**源 APK 的静态脚本已经能支持的结论：**有效出牌经 `iAvatarCombat.useCard` 发送 `requestPlayACard`，参数有 `cID` 和 `tID`；结束回合另发 `avtRequestEndRound`。不是把整个回合的所有操作统一留到最后才提交。拖拽坐标没有放进已定位的出牌参数。

源反馈链可见 `onPushActions → playPushActions → addRawActionGroup`，生命变化消费动作中的 `finalValue`。这是脚本级调用证据，尚不能证明每次 RPC 对应一个底层网络包，也不能假定已还原原客户端全部本地预播放和网络延迟处理。

**UE 重建实施方案：**

1. 拖动、抬牌、指向、取消和合法性提示在客户端即时响应，不随每帧拖动发送网络请求。
2. 合法松手立即提交一次操作意图，锁定该操作的卡牌/目标与序号；不等回包才开始所有视觉反馈。可立即播放可撤销的出牌反馈及起手，是否预播攻击阶段按动作时序和失败恢复能力控制。
3. 怪物受击应跟随对应攻击的命中事件。回包及时到达时先排队到命中点；回包晚到时采用短等待/衔接。对可安全回退的简单受击可做预测反馈，但必须去重，拒绝后能恢复，不能让所有怪物在松手时立刻挨打。
4. 生命、护盾、BUFF、能量、随机结果、死亡、奖励和胜负采用服务端确认结果。客户端可有预测展示，但不提前持久化或发奖励。
5. 超时、拒绝、版本冲突时撤销临时显示、恢复手牌或拉取权威快照；相同操作 ID 重试不重复出牌。断线重进不重复播放已经确认完成的动作。
6. 先量测并验证正常、延迟、拒绝、重复和重连路径，再扩展多段/多目标/反击；不能把降低服务器等待感变成客户端自行决定战斗结果。

## 5. Node.js + MongoDB 服务端计划

采用 so-im 已有的统一连接、模型和服务分层方式，并按游戏领域划分模块。服务端控制规则与持久化，客户端控制输入和表现；原协议研究与 UE 重建 API 分开维护。

| 层/模块 | 具体工作 | 验收要求 |
| --- | --- | --- |
| 应用与连接 | 统一启动、配置、Mongo/Mongoose 连接生命周期、健康检查、PM2 | 同一进程不重复建连接；异常退出可恢复；服务与存储状态可诊断 |
| HTTP 边界 | route/controller 验证参数、身份、错误码，调用领域服务 | 无效/超大/重复请求边界明确，领域逻辑不散落在路由中 |
| 玩家模型 | 档案、角色拥有/成长/服装、编队、卡组、背包与货币 | 默认值和迁移有版本；客户端不能任意写服务端拥有关系 |
| 战斗服务 | 创建战斗、出牌意图、结束回合、动作结果、快照、结束奖励 | 校验卡牌、目标、回合、费用、状态；每次有效操作持久化且可恢复 |
| 规则与配置 | 原配置转结构化定义，技能/BUFF 执行器，固定配置版本 | 一局锁定规则版本；随机过程可复核；原数值与本地补齐规则有来源标记 |
| 进度服务 | 章节/地图/剧情/教程、任务与解锁 | 源字段语义正确，奖励与解锁原子更新，不预填虚假通关记录 |
| 经济服务 | 获取/消耗流水、奖励领取、邮件附件、商店/抽卡 | 幂等、余额校验、关联操作 ID 和审计，不能靠重试重复领取 |
| 活动服务 | 时间配置、任务周期、签到、BOSS/活动状态 | 测试时可注入时钟；跨天、过期、中途重启行为可验证 |
| 运维能力 | 导出/备份/恢复、迁移、日志、配置发布/回滚 | 不触及 so-im 数据；恢复后可重新游玩；敏感值不写日志或入库版本文件 |

MongoDB 是默认主存储。SQLite 仅保留旧存档迁移和历史回归用途。更新用操作 ID、版本条件及必要的原子操作保障一致性；涉及多集合事务时先明确 Mongo 部署条件，不能仅在代码中宣称事务成功。

UE API 的语义应支持多角色、多目标、事件队列和配置版本，不长期固定为“一位英雄打一只怪”。原 `requestPlayACard` 的兼容实现需单独验证消息封装、序列化和实体路由；当前重建 API 不冒称原客户端可直接连接。

## 10. 并行分工与效率约束

在当前并发容量下按三个子任务槽并行，主代理负责整合与验收：

| 工作流 | 责任 | 边界 |
| --- | --- | --- |
| 客户端资源/渲染 | 模型、材质、动画、灯光、VFX、转换与导入脚本 | 先读后改；同一 UE 资产只允许一个写入者；共用材质改动先验证代表样本 |
| 客户端玩法/UI | 源 UI/输入/世界线、战斗表现时序、声音与事件 | 不与渲染任务同时改同一文件；接口改动先约定数据结构 |
| 服务端/Admin | Node/Mongo 领域与接口、Admin 实际业务；子任务槽按当前需要切换 | so-im 只读；管理前后端成对验收；不把后端缺失埋在前端假数据里 |
| 主代理集成 | 源对照、接口一致性、构建、真实客户端操作、阶段验收 | 收敛任务与缺口；不为收集更多资料无限推迟已经能完成的交付 |

复用已有解析器、材质族与导入工具；按源哈希增量处理，不重复全量解包。用小样本解决格式/坐标问题，再批量应用到同类资产。机器清单与截图放 `analysis/`，可复现工具放 `tools/`，只在本计划更新阶段状态和必要的长期决策。

## 11. 完成与质量验收

每个功能的交付必须同时回答：原版依据在哪里、实现了什么、在哪个真实运行环境验证、还缺什么。最低验证组合如下：

| 维度 | 验收内容 |
| --- | --- |
| 来源 | APK 路径/配置行/脚本入口及引用资源可追溯；静态推断、重建规则和原运行结果分开 |
| 视觉 | 相同场景/角色/相近机位对照；布局、大小、颜色、透明、光影、站位、特效时序合格 |
| 交互 | 真实鼠标或触摸完成流程；取消、无效目标、失焦、延迟和返回操作有正确结果 |
| 状态 | 操作确认、存储、重启、奖励幂等、配置版本与审计一致；不能只看 HTTP 200 |
| 资源 | 没有静默丢失模型/贴图/声音；共享资源和缺失引用可定位；原数据保留 |
| 性能 | 在声明的平台和设备上量测；加载、内存、帧率与透明特效开销符合该档位预算 |
| 打包 | 脱离编辑器实际运行；开发路径不泄漏；对应平台的安装与输入分别验证 |

当前没有原版在线服务，也没有原客户端成功运行的完整抓包，因此无法把所有服务端内部规则认证为原版一致。目标是基于可验证的 APK 与原版画面尽量完整重建；缺失处先调查，再采用明确标识、可替换的本地方案。阶段完成以实际可玩与逐项验收为准，不以文档数量、导出文件数量或预览窗口已打开为准。
